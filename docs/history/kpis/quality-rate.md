# kpis/quality-rate.json — history and reasoning

Moved verbatim out of `kpis/quality-rate.json`, where each field now holds its first sentence. The JSON says what a thing is; this file keeps why it became that.

## description

Percentage of good parts out of (good + scrap), computed live on the edge over the CURRENT counter values (IMM counters are cumulative_resettable — this is a since-last-reset ratio, not a shift window; windowed truth lives in historians/postgresql-cagg/oee-hourly.json). INPUT CONTRACT: `calculation.inputs` are canonical names; the binding to each machine type's real wire attribute is `inputMappings[<profileId>] = { <wireAttribute>: <input> }` — exactly the shape of the consumer's KpiFlowOptions.inputMap (i3x-v4 services/kpi-export/src/flow-template.ts), so the exporter can pass `inputMappings[profileIdOfMachine]` straight through. Until it does, the consumer's built-in matcher was SIMULATED against every attribute of both profiles on 2026-07-15: `good`/`scrap` (IMM) and `Act_Amount_PartGood`/`Act_Amount_PartScrap` (CNC) resolve to these inputs with zero false matches. v1 computed on `Good_Parts`/`Scrap_Parts`/`Rework_Parts` — attributes that existed in NO profile and NO source. REWORK IS DELIBERATELY ABSENT: the CNC profile declares Act_Amount_PartRework but NO source feeds it (measured over sources/ + mappings/, 2026-07-15); a required input that never arrives holds the consumer's all-inputs gate open forever and the KPI never fires, silently. When a source feeds rework, add it to inputs + both mappings — ci/lint-kpis.mjs holds the door.
