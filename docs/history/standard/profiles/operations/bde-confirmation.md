# profiles/operations/bde-confirmation.json — history and reasoning

Moved verbatim out of `profiles/erp/bde-confirmation.json`, where each field now holds its first sentence. The JSON says what a thing is; this file keeps why it became that.

## description

CAPT-BDE-CONTRACT (2026-08-03) — the CONFIRMATION grain of the sim-v5 BDE feed, alongside and NOT replacing SMProfile-OperationsResponse. WHY A SECOND PROFILE RATHER THAN MORE ATTRIBUTES ON THE FIRST: the two are different GRAINS of the same producer. sources/rest/erp-operations-response.json polls /api/confirmations?per_po=true — one row per production order, idProperty production_order_no, 17 fields — and that grain is what its consumers (qty reconciliation, order status, OTD) join on. The raw /api/confirmations projection carries 32 fields at one row per BOOKING, so production_order_no repeats and would stop being an identity. Re-pointing the existing source at the raw path would therefore have changed the meaning of an id, silently, behind a one-line path edit. MEASURED 2026-08-03 on the live producer (192.168.178.154:38260) before anything was written: per_po=true returns 100 rows / 100 distinct POs / 17 fields with machine_no non-null on only 32 of 100 (the aggregation loses the machine binding); the raw list returns 32 fields with machine_no non-null on 2000 of 2000 across 81 distinct machines. Fields present ONLY at this grain: shift (1928/2000, values FS + SS observed), labor_min + machine_min + setup_min (2000/2000 each), scrap_reason (123/2000, 2 values), operation_no (1714/2000), confirmation_no, ts_start, rework_qty. PAGING CONTRACT, and it is a trap: the raw endpoint declares NO query parameters in its OpenAPI document, returns a bare JSON array with no total and no cursor, and CAPS SILENTLY AT 5000 ROWS — limit=100000 returns exactly 5000, indistinguishable from a plant with 5000 bookings. An undeclared `offset` IS honoured (verified: offset=5000 returns rows beyond the cap, limit=5000&offset=5000 returns a full second page), so the source pages on limit+offset; `page`, `skip`, `after` and `cursor` are all ignored and silently return page one. NOT MAPPED, DELIBERATELY: worker_id, worker_pnr and operator_id exist as columns on this projection and are NULL on 2000 of 2000 rows, and recorded_by carries a bridge identity (factory-bde-bridge:station:M1-2, 34 distinct) rather than a person. Mapping them would create attributes that are permanently absent AND would open a person-level surface that plans/golden-data-set-cockpit-v2.md §1.3 rules out on purpose: the person axis never resolves below skill x department x shift. When sim-v5 populates a worker reference, it is added HERE only together with that aggregation rule, not before it.

## attributes › shift › description

Shift of record for the booking, derived upstream from machine_departments x machine_pools x shift_config x shift_weekly_pattern (sim-v5, 2026-08-03). MEASURED: 1928 of 2000 rows; values FS and SS observed in that sample. NOT an enum here — only SG runs a night shift, and pinning the observed two would reject NS the first time a night booking arrives.

## attributes › rework_qty › description

Pieces booked for rework — a THIRD disposition, deliberately not folded into scrap (same rule as the part_scrap semantic in mappings/attribute-aliases.json). MEASURED 2026-08-03: 0 on every one of 2000 rows, i.e. the producer emits the column but the plant books no rework yet. Mapped because a real 0 and an absent field are different statements and the consumer must be able to tell them apart.

## attributes › labor_min › description

Personnel minutes booked against this confirmation. MEASURED 2026-08-03: present on 2000 of 2000 rows and NOT a copy of machine_min — median ratio labor/machine is 0.30 over the rows with machine time. This is the only measured personnel quantity in the ERP; ⚠️ CORRECTED 2026-08-03 evening: an earlier version of this description said 'the routing declares no personnel factor at all, so effort is observed retrospectively while it is not planned forward'. That was FALSE and it was read off GET /api/arbeitsplaene, which is a projection that selects none of the labour columns — not off the table. erp.routing declares the planned side on all 582 operations: labor_time_min 582/582, setup_time_min 582/582, required_skill_code + required_skill_level 577/582, labor_cost_per_hour 582/582. Its ratio labor_time_min ÷ (cycle_time_seconds/60) is the planned ATTENDANCE RATIO — 1.00 at manual stations, 0.30 CNC, 0.20 SGM, 0.10 FB. So labor_min HERE is the BOOKED counterpart of a quantity that IS planned forward, and the pair is a real plan-vs-actual comparison rather than the only source of personnel information. The rule that failure produced: an 'X does not exist' claim must name where it was checked, and that place is the schema, never an endpoint.
